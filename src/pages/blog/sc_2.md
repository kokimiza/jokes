Web問題の大半は、リクエストを受けてから応答を返すまでのどこかで、確認すべき処理が抜けている。HTTPリクエスト、ソースコード、DBの表、画面遷移を順に追い、その抜けた処理を特定して直し方を書けるようにするのが、この章の目的だ。

## 1. 出題実績と予想

| 回 | 題材 | 講評で指摘された点 |
|---|---|---|
| 2023秋 問1 | 格納型XSSによる侵害 | DOMを使っているだけで「DOM Based XSS」と答えた誤りが多い |
| 2024春 問1 | APIとJWT | JWTの改ざんの検証方法で、既にある対策を書いた答案が多い |
| 2024春 問3 | XSS・CSRFの連鎖、クラウドの認証情報 | XSSが実行される画面の利用者が管理者だと読み取れていない |
| 2024春 問4 | Linuxの権限とJavaの例外処理 | finally等の、例外時でも必ず実行される処理の理解が浅い |
| 2024秋 問3 | ECサイトの改ざんとカード情報漏えい | XSSの3種類の区別、改ざん内容の過不足 |
| 2024秋 問4 | Web診断（セッション固定化など） | 複数の脆弱性を組み合わせた攻撃の流れを追えていない |
| 2025秋 問1 | CSPの回避と開発プロセス | 開発プロセスを問われて、WAFやログ分析を書いた答案が多い |

講評に繰り返し出てくるのは、脆弱性の名前を知っているかどうかではない。「そのサイトの機能を使うと、攻撃者は次に何ができるか」を追えているかどうかだ。

次回の予想は次のとおり。

- **◎ APIの認可不備**：2024春問1以来、API単位の認可は主題になっていない。BOLA（他人のIDを指定する）とマスアサインメント（送ってはいけない属性を送る）が狙い目。
- **○ SSRFとクラウドのメタデータ**：2022春の午後Ⅱ以来、主題になっていない。クラウド問題と組み合わせやすい。
- **○ ファイルアップロード、パストラバーサル**：2025秋問1でアップロードがCSP回避に使われた。保存先や配信方法まで問われる可能性がある。
- **○ Javaのコード読解**：2022春、2023春、2024春と出たが、2025年度は出なかった。共有変数による競合や例外処理が再び出る可能性がある。

## 2. 認証と認可を分ける

認証は「この利用者は誰か」、認可は「その利用者が、このデータに、この操作をしてよいか」を確かめる処理である。Web問題で最も多い欠陥は、認証はしているのに認可をしていない状態だ。

```
GET /api/orders/10235
Cookie: session=...（利用者Aのセッション）
```

```python
# 欠陥：ログイン済みかどうかしか見ていない
order = db.query("SELECT * FROM orders WHERE id = ?", order_id)

# 修正：所有者をサーバ側で照合する
order = db.query("SELECT * FROM orders WHERE id = ? AND user_id = ?",
                 order_id, session.user_id)
if order is None:
    return 404
```

利用者Aは注文番号を書き換えるだけで、他人の注文を読める。これがIDOR（APIの文脈ではBOLA）で、答案は「注文の所有者がログイン中の利用者と一致するかを、サーバ側で検証していない」と書く。IDを推測しにくいUUIDに変えるのは補助策であり、根本対策としては書かない。

同じ構造の欠陥がほかに二つある。

- **機能単位の認可不備（BFLA）**：管理メニューを画面に出さないだけで、APIの側で役割を確認していない。一般利用者が `POST /api/admin/users/123/role` を直接呼べば管理者になれる。
- **マスアサインメント**：`PUT /api/users/me {"name": "A", "is_admin": true}` のように、リクエストの属性をそのままモデルに代入している。更新してよい属性を許可リストで限定する。

WAFはこれらを防げない。正規の利用者が正規の形式で、IDだけを変えたリクエストを送るので、シグネチャでは区別がつかないからだ。WAFで防げるかを問う設問は繰り返し出ている。

## 3. インジェクション

インジェクションに共通するのは、データとして扱うはずの入力が、SQLやシェルの構文として解釈されることだ。対策も共通で、データと構文を分ける仕組みを使う。

| 種類 | 入力を解釈するもの | 根本対策 |
|---|---|---|
| SQLインジェクション | DB | プレースホルダー |
| OSコマンドインジェクション | シェル | シェルを起動しないAPIを使い、引数を配列で渡す |
| XSS | ブラウザー | 出力する場所に合わせたエスケープ |
| XXE | XMLパーサー | DTD・外部実体の処理を無効にする |
| パストラバーサル | ファイルシステム | 利用者にファイル名を指定させず、IDとの対応表で管理する |

SQLでは、テーブル名や列名、並び順（`ASC`/`DESC`）はプレースホルダーで渡せない。こうした値は、コード内に固定した候補から選ばせる。DBアカウントの権限を絞るのは被害を小さくする追加策で、根本対策の欄には書かない。

## 4. XSS

| 種類 | スクリプトの入り口 | 実行のされ方 |
|---|---|---|
| 反射型 | リクエストのパラメータ | サーバが応答にそのまま埋め込む |
| 格納型 | DBに保存された投稿など | その画面を開いた全員のブラウザーで実行される |
| DOM Based | クライアント側のJavaScript | `innerHTML` などでブラウザーが組み立てる |

2023秋問1では、JavaScriptでDOMを操作していたことにつられて「DOM Based」と答えた受験者が多かった。区別の基準は、スクリプトを含むHTMLを組み立てたのがサーバかブラウザーかである。サーバが保存済みのデータをそのまま出力していれば、DOMを使っていても格納型になる。

XSSの被害を「Cookieを盗まれる」だけで止めない。2024春問3では、XSSが実行される問合せ管理画面を開くのは管理者だった。管理者のブラウザーでスクリプトが動けば、管理者の権限でロール変更や会員情報の取得ができる。HttpOnlyはCookieの読取りを防ぐが、こうした操作は防がない。

## 5. ブラウザーの仕組み

### 5.1 同一オリジンポリシーとCORS

オリジンは「スキーム・ホスト・ポート」の組である。同一オリジンポリシーは、別オリジンの応答をJavaScriptで**読む**ことを制限する。リクエストの**送信**は止めない。CSRFが成立するのはこのためだ。

CORSは、サーバが「このオリジンからなら応答を読んでよい」と宣言する仕組みである。よくある設定ミスは、リクエストの `Origin` をそのまま `Access-Control-Allow-Origin` に返し、`Access-Control-Allow-Credentials: true` も付けているもの。これでは任意のサイトから、ログイン中の利用者の権限で応答を読まれる。

### 5.2 CSRF

CSRFが成立する条件は三つある。利用者がログイン済みでCookieが自動で送られること、状態を変える処理が推測できるリクエストだけで実行できること、サーバが送信元を確かめていないこと。

対策は、推測できないトークンをフォームに埋め込んでサーバで照合することだ。2024春問3では、攻撃者がトークンを取得した後にどう悪用するかまで問われた。トークンがセッションに結び付いているか、別のセッションのトークンでも通らないかを確かめる。

Cookieの `SameSite=Lax` も効くが、別サイトからのトップレベルのGET遷移ではCookieが送られる。GETで状態を変えない設計とセットで使う。

### 5.3 Cookieとセッション

| 属性 | 効果 | 付けないと |
|---|---|---|
| `Secure` | HTTPSのときだけ送る | 平文の通信で盗聴される |
| `HttpOnly` | JavaScriptから読めない | XSSでCookieを読まれる |
| `SameSite` | 別サイトからのリクエストに付けるか | CSRF |
| `Domain` | 送る範囲（指定しないと発行元ホストだけ） | 広く指定するとサブドメインにも送られる |

セッション固定化は、ログイン前に発行したセッションIDをログイン後も使い続けることで成立する。ログインに成功した時点でIDを作り直す。2024秋問4でも問われ、正答率は高かった。

### 5.4 CSP

```
Content-Security-Policy: script-src 'nonce-r4nd0m' 'strict-dynamic'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'
```

`script-src` は実行してよいスクリプトの取得元、nonceは応答ごとに変わる値を持つscript要素だけを許可する指定、`frame-ancestors` は自ページを埋め込めるページの指定（クリックジャッキング対策）である。

CSPが効かなくなるのは次のような場合だ。

- `'unsafe-inline'` を許可している。
- nonceが固定値か、推測できる。
- 許可したオリジンに、利用者がファイルを置ける。
- 許可したオリジンに、応答の中身を呼出し側が決められるエンドポイント（JSONPなど）がある。

2025秋問1は三つ目の例だった。`script-src 'self'` でも、同じサイトにアップロードしたファイルをスクリプトとして読み込ませられれば、CSPは通ってしまう。CSPは被害を減らす追加策で、根本対策は出力時のエスケープである。

## 6. サーバ側から内部へ向かう攻撃

### 6.1 SSRF

画像の取込み、Webhook、URLのプレビューのように、利用者が指定したURLにサーバがアクセスする機能を悪用する。外部からは届かない宛先に、サーバ自身から接続させる。

狙われるのは、送信元IPアドレスで守っている社内APIや管理画面と、クラウドのメタデータサービスだ。メタデータサービスからは、そのサーバに割り当てられた一時的な認証情報を取れる場合がある。

対策は次のとおり。

- 宛先は許可リストで限定する。拒否リストはリダイレクトやDNSの再解決で回避される。
- 名前解決した後のIPアドレスで判定し、プライベートアドレスやリンクローカルアドレスを拒否する。
- メタデータへのアクセスにトークンを必須にする（AWSのIMDSv2など）。
- サーバから外への通信をFWで絞る。

### 6.2 ファイルアップロード

拡張子と `Content-Type` は偽装できるので、中身を検査する。保存先は公開ディレクトリの外にし、そこではスクリプトを実行させない。ファイル名はサーバ側で付け直す。配信するときの `Content-Type` と `X-Content-Type-Options: nosniff` も確認する。

### 6.3 プロキシとキャッシュの解釈の違い

HTTPリクエストスマグリングは、フロントのプロキシとバックエンドで `Content-Length` と `Transfer-Encoding` の解釈が違うことを使う。キャッシュポイズニングは、キャッシュキーに含まれないヘッダーで応答が変わることを使う。どちらも、構成図にリバースプロキシやCDNがあるときに疑う。

## 7. JWT

| 検証項目 | 欠けると |
|---|---|
| 署名 | 改ざんしたトークンを受け入れる |
| `alg` の固定 | `none` や想定外のアルゴリズムへの差替えを受け入れる |
| `iss` | 別の発行者のトークンを受け入れる |
| `aud` | 別のサービス向けのトークンを流用される |
| `exp` | 漏えいしたトークンを期限なく使われる |

署名付きJWTのペイロードはBase64URLで符号化されているだけで、誰でも読める。機密情報は入れない。共通鍵（HS256）で署名している場合、その鍵を持つ者は誰でも正規のトークンを作れる。

ログインの試行やIDの列挙、データの大量取得には、利用者・IPアドレス・APIキーの単位でレート制限をかける。

## 8. Webスキミング

決済画面に不正なスクリプトを入れ、入力されたカード情報を外に送らせる攻撃である。

| 侵入経路 | 対策 |
|---|---|
| 管理画面への不正ログインやCMSの脆弱性でサイトを改ざん | 管理画面の接続元制限、MFA、改ざん検知 |
| 外部から読み込むスクリプトの改ざん | SRI、外部スクリプトを減らす |
| 送信先の追加 | CSPの `connect-src`、`form-action` |

2024秋問3では、カード情報がクエリパラメータで送られていたため、Webサーバのアクセスログに残っていた。そこから被害を受けた利用者を特定できる。「盗聴された」「キーロガー」と答えた誤答が多かった。ログに何が残るかを本文から読む。

カード情報を自社のサーバで受けない方式（決済代行の画面へ遷移する、トークン化する）も、根本対策としてよく問われる。

## 9. 開発プロセスと診断

| 手法 | 対象 | 向いていること |
|---|---|---|
| SAST | ソースコード | 実行せずに解析でき、開発の早い段階で使える |
| DAST | 動いているアプリ | 外からリクエストを送るので、設定の不備も見つかる |
| IAST | テスト実行中のアプリ内部 | 内部のデータの流れも観測できるが、テストで通らない経路は見ない |
| SCA | 依存ライブラリ | 既知の脆弱性とライセンスを検出する |

2025秋問1では「脆弱性を検出して修正する開発プロセス」を問われ、WAFの導入やIDの棚卸しを書いた答案が多かった。プロセスを聞かれたら、仕様を理解した人によるレビューや診断、指摘の修正、修正後の再テストといった工程で答える。

診断の問題では、どこから攻撃し、どこで結果を確かめるかが問われる。

- 認可は、権限の違う二つのアカウントで同じデータを操作して比べる。
- 格納型XSSは、入力した画面ではなく、その値を表示する別の画面（管理者用の画面を含む）で確認する。
- 管理LANから診断した結果を、インターネットからの攻撃にそのまま当てはめない。

## 10. コードを読む

### 10.1 プレースホルダーと認可は別の対策

```java
String sql = "SELECT * FROM orders WHERE order_no = ? AND customer_id = ?";
try (PreparedStatement stmt = conn.prepareStatement(sql)) {
    stmt.setString(1, request.getParameter("orderNo"));
    stmt.setString(2, sessionCustomerId);
    try (ResultSet rs = stmt.executeQuery()) {
        // 応答を組み立てる
    }
}
```

`PreparedStatement` と `setString` で値を構文から分けているので、SQLインジェクションは防げている。それとは別に、`customer_id = ?` の条件で対象を自分の注文に限っている。この値はリクエストのパラメータからではなく、サーバが検証したセッションから取る。try-with-resourcesは、例外が起きても接続を閉じる。

### 10.2 共有変数による競合

サーブレットのように、複数のリクエストが一つのインスタンスを共有する環境で、リクエストごとの値をインスタンス変数や `static` 変数に入れると、別の利用者の処理に上書きされる。

1. 利用者Aの処理が、共有変数に注文Aの番号を入れる。
2. 利用者Bの処理が、同じ変数を注文Bの番号で上書きする。
3. Aの処理が共有変数を読み、注文Bを返す。

リクエストごとの値はローカル変数に置き、引数で渡す。2023春の午後Ⅰ問1がこの題材だった。

### 10.3 例外処理と権限

2024春問4では、例外が起きたときに後始末をする処理（`finally` やtry-with-resources）を書けるかが問われた。途中で失敗したとき、ファイル、DB接続、一時的に上げた権限が残らないかを追う。Linuxでは、ファイルの所有者・グループ・その他の `rwx` と、ディレクトリの `x`（中に入る権限）も読む。
