認証の問題にはシーケンス図がよく出る。矢印ごとに「何が送られ、受け取った側が何を検証しているか」を書き込めれば、ほとんどの設問に答えられる。方式の名前よりも、検証する主体と鍵の置き場所を見る。

## 1. 出題実績と予想

| 回 | 題材 | 講評で指摘された点 |
|---|---|---|
| 2023秋 問2 | サーバ証明書の検証、秘密鍵の管理、無線LAN | 偽サイトでもHTTPSなら証明書の検証で失敗する、という点を書けていない |
| 2023秋 問3 | CI侵害、WebAuthn、HSM | WebAuthnをクライアント証明書認証などと取り違えた。「電子署名を暗号化できる」等の誤解 |
| 2024春 問2 | 多要素認証の突破 | 攻撃の手順が足りない、別の攻撃を答えた |
| 2025春 問3 | スマホアプリ、プライベートCA、署名付きURL | 署名付きURLをアプリ内で作ると答えた（秘密情報はサーバで扱う） |
| 2025秋 問2 | 暗号資産交換業の鍵管理 | 「デジタル署名」と答えた誤りが多い。パスワードと暗号文を同時に取られる場合を見落とす |
| 2025秋 問3 | ネットバンキング、ハードウェアトークン、認証基盤 | スマートフォン故障時に、強度を落とさない代替策を答える |

次回の予想は次のとおり。

- **◎ パスキーとフィッシング耐性**：2025年は、リアルタイムフィッシングによる証券口座の乗っ取りが相次いだ。OTPでは防げない理由と、パスキーなら防げる理由を、検証の仕組みから説明させる問題は作りやすい。端末をなくしたときの復旧手順もあわせて出そうだ。
- **◎ OAuth／OIDC**：2021春、2022春、2023春と旧形式では毎年のように出ていたが、新形式ではまだ主題になっていない。stateやPKCE、IDトークンとアクセストークンの区別が狙われる。
- **○ 鍵の保管と暗号の使い分け**：2025秋問2の講評は、暗号技術の基本的な理解の不足を指摘している。MACと署名、鍵を暗号化する鍵を区別しておく。

## 2. パスキー（FIDO2／WebAuthn）

### 2.1 登場する主体

| 主体 | 役割 |
|---|---|
| 認証器 | 秘密鍵を持ち、署名する（スマートフォン、セキュリティキー、PCのTPMなど） |
| ブラウザー・OS | Webサービスと認証器の間を取り次ぎ、アクセス先のオリジンを確かめる |
| RP（Webサービス） | 公開鍵を保存し、署名を検証する |

登録のとき、認証器は利用者を確認（生体認証やPIN）してから、サービス（RP ID）ごとに鍵ペアを作る。RPに送るのは公開鍵だけである。認証のときは、RPが送ったチャレンジに認証器が秘密鍵で署名し、RPが公開鍵で検証する。

### 2.2 フィッシングに強い理由

- 鍵はRP IDに結び付いている。偽サイトは別のドメインなので、正規サイト用の鍵が使われない。
- 署名するデータにオリジンが含まれ、RPがそれを確かめる。
- チャレンジは毎回違うので、署名を使い回せない。
- RPには公開鍵しかないので、RPから漏れてもなりすましには使えない。

| 方式 | フィッシング耐性 | 理由 |
|---|---|---|
| パスワード | ない | 偽サイトに入力した値をそのまま使われる |
| SMS・アプリのOTP | 弱い | 偽サイトが有効期間内に正規サイトへ中継すれば通る |
| プッシュ通知の承認 | 弱い | 通知を大量に送って承認させる攻撃がある。番号の照合で緩和できる |
| パスキー | 強い | オリジンの検証と、サービスごとの鍵 |

答案で「秘密鍵が外に出ないから」とだけ書くと足りない。2019春の午後Ⅰ問2の講評も、この書き方を指摘している。中継攻撃に強い理由は、正規のサービスに結び付いた署名データを、受け取る側が検証することにある。

### 2.3 同期パスキーと端末固定のパスキー

同期パスキーは、クラウドのアカウントを通じて複数の端末で使える。端末をなくしても困らないが、安全性はその同期用アカウントに依存する。端末固定のものは秘密鍵が1台から出ないが、紛失に備えて複数の認証器を登録しておく必要がある。生体情報は認証器の中で照合され、サービスには送られない。

### 2.4 復旧の手順も認証方式の一部

スマートフォンの故障や機種変更のときに、窓口でMFAを外す、パスワードだけのログインに戻す、といった運用をすると、強い認証を入れた意味が薄れる。2025秋問3では、本文の認証基盤で使える範囲から、強度を落とさない代替策を選ばせた。予備の認証器を事前に登録する、本人確認をしたうえで再登録する、古い資格情報を無効にする、の三つが基本になる。

本人確認（申込み時に誰かを確かめる）、当人認証（登録済みの本人がアクセスしているかを確かめる）、取引の承認（誰にいくら送るかを本人に確かめる）は、それぞれ別の処理である。ログインが正しくても、攻撃者に誘導されて別の送金を承認させられれば被害が出る。2025秋問3では、振込みの流れとハードウェアトークンの特徴から、どんな攻撃が成り立つかを考えさせた。

## 3. OAuth 2.0 と OpenID Connect

### 3.1 違い

| | OAuth 2.0 | OpenID Connect |
|---|---|---|
| 目的 | APIを使う権限を委ねる（認可） | 利用者が誰かを伝える（認証） |
| 主なトークン | アクセストークン | IDトークン（JWT） |
| トークンを受け取って検証する側 | API（リソースサーバ） | クライアント（RP） |

アクセストークンをログインの証明に使うのは誤りである。別のクライアント向けに発行されたトークンかもしれないからだ。ログインにはIDトークンを使い、`aud` が自分のクライアントIDであることを確かめる。

### 3.2 認可コードフローとPKCE

1. クライアントが乱数 `code_verifier` を作り、そのハッシュ値を `code_challenge` にする。
2. ブラウザーを認可サーバへリダイレクトする。`client_id`、`redirect_uri`、`state`、`nonce`、`code_challenge` を付ける。
3. 認可サーバが利用者を認証し、同意を得る。
4. 認可サーバが `redirect_uri` へ、認可コードと `state` を付けて戻す。
5. クライアントが `state` を照合する。
6. クライアントが、ブラウザーを通さない通信で、認可コードと `code_verifier` を送る。
7. 認可サーバは `code_verifier` のハッシュ値が `code_challenge` と一致するかを確かめ、トークンを返す。

| パラメータ | 防ぐもの | 検証する主体 |
|---|---|---|
| `state` | 攻撃者の認可コードを被害者のセッションに結び付けるCSRF | クライアント |
| `nonce` | IDトークンの再利用 | クライアント |
| PKCE | 認可コードの横取り | 認可サーバ |
| `redirect_uri` の完全一致 | 認可コードを攻撃者のURLへ送らせる | 認可サーバ |

`redirect_uri` を前方一致やワイルドカードで確認していると、攻撃者が用意したパスやサブドメインへ認可コードが送られる。事前に登録したURIと完全に一致させる。

なお、[OAuthのセキュリティBCP（RFC 9700）](https://www.rfc-editor.org/rfc/rfc9700.html)では、条件を満たせばPKCEをCSRF対策としても使えるとしている。「PKCEはCSRFと無関係」とは覚えない。

### 3.3 トークンが盗まれたとき

アクセストークンの多くはBearerトークンで、持っている者なら誰でも使える。アクセストークンの有効期限を短くし、リフレッシュトークンで更新する。リフレッシュトークンは使うたびに新しくし、古いものがもう一度使われたら盗難とみなして一式を失効させる。DPoPやmTLSで、トークンを特定の鍵に結び付ける方法もある。

デバイスコードフロー（テレビなど入力しにくい機器向け）は、攻撃者が取ったコードを被害者に入力させるフィッシングに使われる。使わないなら無効にしておく。

## 4. SAML

IdPが利用者を認証してアサーションを発行し、SPがそれを検証する。SPが確かめるのは、署名、`Audience`（自分宛てか）、有効期限、`InResponseTo`（自分が出した要求への応答か）、`Destination` である。

IdPの署名鍵が漏れると、攻撃者は任意の利用者のアサーションを作れ、連携するすべてのSPに入られる。IdPは最も厳重に守る資産になる。

## 5. 証明書と署名

### 5.1 サーバ証明書の検証

ルートCA、中間CA、サーバ証明書の順に、上位の秘密鍵で下位の証明書に署名している。検証する側は次を確かめる。

- 信頼するルートCAまで署名をたどれるか
- 有効期間内か
- アクセス先のホスト名がSANに含まれるか
- 失効していないか（CRL、OCSP）

2023秋問2の講評のとおり、攻撃者が偽サイトを用意しても、HTTPSでアクセスしていれば証明書の検証で失敗する。逆に言えば、検証を省いたクライアントや、攻撃者のルート証明書を入れた端末では成立してしまう。2025春問3では、プライベートCAのルート証明書を端末に入れて検証エラーを消す方法が問われた。TLSインスペクションも同じ仕組みを使う。

### 5.2 デジタル署名とMAC

署名は送信者の秘密鍵で作り、受信者が公開鍵で検証する。改ざんされていないこと、その秘密鍵の持ち主が作ったこと、否認できないことを確かめられる。MAC（HMACなど）は共通鍵で作って共通鍵で検証するので、鍵を持つ双方が作れる。第三者に対して「相手が作った」と示すことはできない。

「署名を暗号化する」「秘密鍵が漏えいしても安全」といった書き方は、2023秋問3の講評で誤りとして挙げられた。どの鍵を誰が持ち、誰が何を作れるかから考える。

## 6. 鍵の管理

暗号アルゴリズムが破られるより、鍵が漏れるほうがはるかに起こりやすい。出題も鍵の扱いに集中している。

| 段階 | 確かめること |
|---|---|
| 生成 | 十分な乱数で作る。HSMの中で作れば外に出ない |
| 保管 | ソースコードや設定ファイルに書かない。HSM、KMS、シークレット管理サービスに置く |
| 利用 | 署名用と暗号化用、本番と検証で鍵を分ける。使える人とサービスを絞り、利用を記録する |
| 更新 | 定期的に、また漏えいの疑いがあれば更新する |
| 廃棄 | 証明書を失効させ、鍵を確実に消す |

エンベロープ暗号化では、データをデータ鍵で暗号化し、データ鍵を別の鍵（鍵暗号化鍵）で暗号化して保存する。鍵暗号化鍵はKMSやHSMで守る。データ鍵そのものが漏れた場合は、鍵暗号化鍵を替えても既に漏れたデータ鍵は無効にならず、データの暗号化をやり直す必要がある。

パスワードを鍵にしてデータを暗号化する場合、暗号文とパスワードを同じ場所に置けば、両方を一度に取られる。2025秋問2の講評はこの点を指摘している。

パスワードを保存するときは、利用者ごとのソルトを付け、計算に時間のかかる関数（Argon2id、bcrypt、scrypt、PBKDF2）でハッシュ化する。SHA-256を1回かけただけでは、計算が速すぎて総当たりに弱い。

## 7. パスワードへの攻撃

| 攻撃 | やり方 | 対策と限界 |
|---|---|---|
| 総当たり | 一つのIDに多数の候補を試す | 試行回数の制限。ハッシュを持ち出されたオフライン解析には効かない |
| パスワードリスト攻撃 | 他所で漏れたIDとパスワードの組を試す | 使い回しの防止、MFA |
| パスワードスプレー | 多数のIDに、よくあるパスワードを少しずつ試す | ID単位のロックでは止まらない。複数IDへの試行をまとめて検知する |
| リアルタイムフィッシング | 偽サイトで入力させた値を、その場で正規サイトに中継する | OTPでも中継される。パスキーなどオリジンを検証する方式にする |

オンラインの攻撃とオフラインの解析を混同した答案は、2022春の午後Ⅱ問2で指摘された。ロックアウトはサーバに対する試行にしか効かない。

## 8. 特権とネットワーク接続の認証

条件付きアクセスは、利用者、端末の状態、場所、ログインのリスクから、許可・MFAの要求・拒否を決める。特権は必要なときに期限付きで与え（JIT）、特権IDの貸出しと操作をまとめて記録する（PAM）。人事システムと連携してアカウントを自動で作成・停止すると（SCIM）、退職者のアカウントが残らない。

Windowsのドメインでは、NTLMのハッシュ値をそのまま使って別の端末にログオンするPass-the-Hashがある。特権アカウントで一般の端末にログオンしない、ローカル管理者のパスワードを端末ごとに変える（LAPS）、が基本の対策になる。

802.1XのEAP-TLSでは、端末（サプリカント）と認証サーバ（RADIUS）が互いに証明書で認証する。端末がRADIUSサーバの証明書を検証しないと、偽のアクセスポイントにつながってしまう。端末の秘密鍵はエクスポートできない設定にするか、TPMに置く。2023秋問2の後半はこの題材だった。

SSHでは、ホスト鍵の確認（接続先が本物か）と、利用者の公開鍵認証（利用者が本物か）は別の処理である。秘密鍵のパスフレーズは手元で秘密鍵を復号するためのもので、サーバには送らない。2021秋の午後Ⅰ問1で問われた。
