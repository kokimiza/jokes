## 2. FIDO2 / WebAuthn / パスキー

### 2.1 登場主体

| 主体 | 役割 |
|---|---|
| 認証器（Authenticator） | 秘密鍵を保持し、署名する（スマートフォン、セキュリティキー、PC内蔵のTPMなど） |
| クライアント（ブラウザー・OS） | RPと認証器を仲介し、**オリジンを確認する** |
| RP（Relying Party） | 公開鍵を保存し、署名を検証するWebサービス |

### 2.2 登録と認証の流れ

**登録**

1. RPがチャレンジ（乱数）とRP IDを送る
2. 認証器が利用者検証（生体認証やPIN）を行い、**RP IDごとに** 鍵ペアを生成する
3. 公開鍵とクレデンシャルIDをRPに送る。秘密鍵はRPには送らない。同期型では、保護された仕組みで他の認証器へ同期される場合がある

**認証**

1. RPがチャレンジを送る
2. ブラウザーが、アクセス中のオリジンとRP IDの対応を確認する
3. 認証器が利用者検証の後、チャレンジなどに秘密鍵で署名する
4. RPが保存済みの公開鍵で署名を検証する。チャレンジとオリジンが一致するかも確認する

### 2.3 なぜフィッシングに強いのか

- 鍵がRP IDに結び付いているため、偽サイト（別のドメイン）では正規サイト用の鍵が使われない。
- 署名データにオリジンが含まれ、RPが検証する。
- チャレンジが毎回異なるため、署名を使い回せない（リプレイ耐性）。
- RPが保存するのは公開鍵だけなので、RPから漏えいしても、なりすましには使えない。

| 方式 | フィッシング耐性 | 理由 |
|---|---|---|
| パスワード | なし | 偽サイトに入力された値がそのまま使える |
| OTP（SMS、TOTP） | 弱い | 偽サイトが中継すれば、有効期間内に使われる（リアルタイムフィッシング） |
| プッシュ通知 | 弱い | 大量に通知を送って承認させる攻撃（MFA疲労）。番号照合で緩和 |
| FIDO2 / パスキー | 強い | オリジンの検証と、ドメインごとの鍵 |

### 2.4 パスキーの種類

| 種類 | 特徴 | 考慮点 |
|---|---|---|
| デバイス固定型 | 秘密鍵が1台の認証器から出ない | 紛失時の復旧手段（複数登録）が必要 |
| 同期型 | クラウドのアカウントを通じて複数の端末に同期 | 同期元アカウントのセキュリティに依存する |

利用者検証（User Verification）は、認証器を持っている人が本人であることを確かめる手順。生体情報は認証器の中で照合され、RPには送られない。

## 3. OAuth 2.0 と OpenID Connect

### 3.1 OAuthとOIDCの違い

| | OAuth 2.0 | OpenID Connect |
|---|---|---|
| 目的 | **認可**：APIへのアクセス権を委譲する | **認証**：利用者が誰かを伝える |
| 主なトークン | アクセストークン | IDトークン（JWT） |
| トークンの受け手 | リソースサーバ（API） | クライアント（RP） |

**誤用の典型**：アクセストークンを「ログインの証明」として使う。アクセストークンは別のクライアント向けに発行されたものかもしれず、利用者の認証には使えない。認証にはIDトークンを使い、`aud` が自分のクライアントIDであることを検証する。

### 3.2 登場主体

| 主体 | 役割 |
|---|---|
| リソースオーナー | 利用者 |
| クライアント | 利用者の代わりにAPIを使うアプリ |
| 認可サーバ | 利用者を認証し、トークンを発行する（OIDCではOP / IdP） |
| リソースサーバ | アクセストークンを検証してAPIを提供する |

### 3.3 認可コードフロー＋PKCE

1. クライアントが `code_verifier`（乱数）を生成し、そのハッシュ値を `code_challenge` とする
2. ブラウザーを認可サーバへリダイレクトする（`client_id`、`redirect_uri`、`state`、`nonce`、`code_challenge` を付ける）
3. 認可サーバが利用者を認証し、同意を得る
4. 認可サーバが `redirect_uri` に認可コードと `state` を付けてリダイレクトする
5. クライアントが `state` を照合する
6. クライアントが **バックチャネル** で認可コードと `code_verifier` を送り、トークンを受け取る
7. 認可サーバは `code_verifier` のハッシュ値が `code_challenge` と一致するか検証する

### 3.4 各パラメータが防ぐもの

| パラメータ | 防ぐ攻撃 | 検証する主体 |
|---|---|---|
| `state` | CSRF（攻撃者の認可コードを被害者のセッションに紐付ける） | クライアント |
| `nonce` | IDトークンのリプレイ | クライアント（IDトークン内の値と照合） |
| PKCE | 認可コードの横取り（不正なアプリ、ログへの記録） | 認可サーバ |
| `redirect_uri` の完全一致 | 認可コードを攻撃者のURLに送らせる | 認可サーバ |

`redirect_uri` を前方一致やワイルドカードで検証していると、攻撃者が用意したパスやサブドメインに認可コードが送られる。**事前に登録したURIとの完全一致** が原則である。

### 3.5 トークンの保護

- **Bearerトークン**：持っている者は誰でも使える。漏えいするとそのまま再利用される（Token Replay）。
- **有効期限**：アクセストークンは短く、リフレッシュトークンで更新する。
- **リフレッシュトークンのローテーション**：使うたびに新しいものを発行し、古いものが再度使われたら、盗難と判断して一連のトークンを失効させる。
- **送信者制約（Sender-Constrained）**：DPoPやmTLSでトークンを鍵に結び付け、鍵を持たない者には使えなくする。

### 3.6 補強（C）

- **Device Code Flow**：入力しにくい機器向け。攻撃者が取得したコードを被害者に入力させ、トークンを攻撃者に発行させるフィッシングに注意する。不要なら無効にする。
- **PAR**：認可リクエストをバックチャネルで事前に登録し、ブラウザーにはその参照だけを渡す。改ざんや情報漏えいを防ぐ。
- **JAR / JARM**：認可リクエスト・応答をJWTで署名する。

## 4. SAML 2.0

| 主体 | 役割 |
|---|---|
| IdP | 利用者を認証し、Assertion（属性や認証結果）を発行する |
| SP | Assertionを検証してサービスを提供する |

SPが検証すべき項目：

| 項目 | 欠落した場合 |
|---|---|
| 署名 | 改ざんしたAssertionを受け入れる |
| `Audience` | 別のSP向けのAssertionを流用される |
| `NotOnOrAfter` などの有効期間 | 古いAssertionを再利用される |
| `InResponseTo` | SPが発行していない要求への応答を受け入れる |
| `Destination` / `Recipient` | 別の宛先向けのAssertionを受け入れる |

**IdPの署名鍵が漏えいした場合**、攻撃者は任意の利用者のAssertionを作成でき、連携しているすべてのSPに影響する。IdPはSSOの単一障害点であり、最も厳重に保護すべき資産である。

## 5. PKIと証明書

### 5.1 信頼の連鎖

ルートCA → 中間CA → サーバ証明書 の順に、上位の秘密鍵で下位の証明書に署名する。検証する側は、トラストストアに登録されたルートCA証明書まで辿れるかを確認する。

サーバ証明書の検証項目：

- 信頼できるルートCAまで署名を辿れるか
- 有効期間内か
- アクセス先のホスト名がSAN（Subject Alternative Name）に含まれているか
- 失効していないか（CRL、OCSP）
- 用途（Key Usage、Extended Key Usage）が適切か

### 5.2 失効の確認

| 方式 | 仕組み | 特徴 |
|---|---|---|
| CRL | CAが失効した証明書の一覧を公開する | リストが大きくなる。更新の間隔だけ遅れる |
| OCSP | 個別の証明書の状態を問い合わせる | 問合せ先が利用者のアクセス先を知ることができる。応答できないと可用性に影響 |
| OCSPステープリング | サーバがOCSP応答を取得してTLSハンドシェイクで提示する | クライアントの問合せが不要 |

### 5.3 デジタル署名

- 送信者が **秘密鍵** で署名し、受信者が **公開鍵** で検証する。
- 確認できること：完全性（改ざんされていない）、真正性（その秘密鍵の持ち主が署名した）、否認防止。
- 公開鍵が本当にその相手のものであることは、証明書（CAの署名）で保証する。

## 6. 鍵の管理（2025年度関連）

鍵の管理は「暗号アルゴリズムの強さ」よりも出題されやすい。暗号が破られるより、鍵が漏えいする方がはるかに現実的だからである。

| ライフサイクル | 確認すること |
|---|---|
| 生成 | 十分な乱数性。HSMの内部で生成し、外に出さない |
| 保管 | ソースコードや設定ファイルに直書きしない。HSM、KMS、シークレット管理サービスに保管する |
| 利用 | 用途ごとに鍵を分ける（署名用と暗号化用、環境ごと） |
| ローテーション | 定期的、および漏えいの疑いがあるときに更新する。旧鍵での検証期間を設ける |
| 失効・破棄 | 証明書の失効、鍵の確実な削除 |
| アクセス制御 | 鍵を使える人・サービスを限定し、利用をログに残す |

| 機構 | 特徴 |
|---|---|
| HSM | 耐タンパー性を持つ専用装置。秘密鍵を外部に出さずに署名・復号する |
| TPM | PCのマザーボードに搭載されるチップ。端末に紐付けた鍵の保管、起動時の完全性の計測 |
| Secure Enclave | スマートフォンなどのSoC内の隔離領域 |
| クラウドKMS | 鍵の管理と利用をAPIで提供。IAMで利用者を制御する |

**エンベロープ暗号化**：データをデータ鍵（DEK）で暗号化し、DEKを鍵暗号化鍵（KEK）で暗号化して保存する。KEKはKMSやHSM等で保護する。KEKを替える場合は、ラップ済みDEKを再ラップする方法や旧KEKを復号用に保持する方法がある。DEK自体が漏えいした場合は、KEKだけ替えても既に漏れたDEKと暗号文を無効にはできず、データの再暗号化等が必要になる。

### 6.1 パスワードの保存

- 平文や可逆な暗号化で保存しない。
- 単純なハッシュ関数（SHA-256の1回だけなど）は高速すぎるため、総当たりに弱い。
- **ソルト**（利用者ごとの乱数）で、同じパスワードが同じ値にならないようにし、事前計算表による解析を防ぐ。
- **計算コストを調整できる関数**（Argon2id、bcrypt、scrypt、PBKDF2）を使う。

## 7. 特権とアクセス制御

| 用語 | 内容 |
|---|---|
| RBAC | 役割に権限を割り当てる |
| ABAC | 利用者・資源・環境の属性で判断する（部署、機密度、時間帯、端末の状態） |
| 条件付きアクセス | 利用者、端末の準拠状態、場所、サインインのリスクに応じて、許可・MFAの要求・拒否を決める |
| JIT | 特権を必要なときだけ、期限付きで付与する |

| PAM | 特権IDの貸出し・承認・操作の記録を一元管理する |

## 8. Windows・AD環境の認証（C）

[sc_5](/blog/sc_5) のインシデント対応と関連する。

- **Kerberos**：KDCが発行するTGTで、サービスチケットを取得する。相互認証が可能。
- **Pass-the-Hash**：NTLM認証では、パスワードの代わりにハッシュ値そのものが認証に使える。端末から窃取されたハッシュ値で、別の端末にログオンされる。
- **Pass-the-Ticket**：窃取したKerberosチケットの再利用。

対策の方向性：特権アカウントで一般端末にログオンしない（階層化）、ローカル管理者のパスワードを端末ごとに変える（LAPS）、NTLMの制限、Credential Guardなどによる資格情報の保護。

## 9. ネットワーク接続の認証：802.1X / EAP-TLS

| 主体 | 役割 |
|---|---|
| サプリカント | 端末 |
| オーセンティケーター | 無線LANのアクセスポイント、スイッチ |
| 認証サーバ | RADIUSサーバ |

- EAP-TLSは、**クライアント証明書** とサーバ証明書の両方で相互に認証する。パスワードを使わない。
- 端末は、RADIUSサーバの証明書を検証すべきである。検証しないと、偽のアクセスポイントと偽の認証サーバに接続してしまう。
- 証明書を端末にインストールする際、秘密鍵をエクスポートできない設定にすると、別の端末への持出しを防げる。TPMに保管するとさらに強い。

## 11. 認証を破る方法と、その対策が効く範囲

2021年春午後Ⅱ問1と2021年秋午後Ⅰ問2では、パスワード攻撃の種類や前提の取り違えが講評で指摘された。2022年春午後Ⅱ問2では、オフライン解析とオンライン攻撃の混同が指摘されている。

| 攻撃 | 試すもの | 有効な対策と限界 |
|---|---|---|
| 総当たり | 一つのID等に多数の候補 | オンラインでは試行制限。ハッシュを持ち出されたオフライン解析にはサーバのロックアウトは効かない |
| パスワードリスト攻撃 | 他所から流出したID・パスワードの組 | 使い回し防止、MFA、漏えいパスワードの利用抑止 |
| パスワードスプレー | 多数のIDに少数のよくあるパスワード | ID単位のロックアウトだけでは足りない。複数IDにまたがる試行を検知 |
| リアルタイムフィッシング | 偽サイトで入力させたパスワード・OTPを即時中継 | OTPの有効期限を短くしても中継は可能。RPとの結び付きを検証する認証を検討 |
| オフライン解析 | 漏えいしたハッシュ等に候補を照合 | 十分な強度のパスワード、ソルト、適切な計算コスト |

**答案の修正例**：「OTPだから再利用できない」→「OTPを有効期間内に中継されると正規サーバで認証が通る」。フィッシング耐性の理由では「秘密鍵が漏れない」だけでなく、**正規RPに結び付いた署名データを、受け手が検証すること** まで書く。2019年春午後Ⅰ問2は、この説明の練習になる。

### 11.1 本人確認・ログイン・取引承認を分ける

- 本人確認：登録時などに、申込者が誰であるかを確認する。2022年春午後Ⅰ問3の公的個人認証・撮影を用いた確認が例。
- 当人認証：登録済みの利用者がアクセスしているかを確認する。
- 取引承認：誰にいくら送るかなど、重要操作の内容を本人に確認させる。ログインが正しくても、攻撃者の指示で別の送金を承認すれば被害が起こる。

**復旧経路も認証方式の一部**。スマートフォンの故障・紛失、退職、端末更新の際に、本人確認を省略したMFA解除や共用IDへの切替えを認めると、通常ログインを強化した効果が薄れる。代替要素の事前登録、厳格な再登録、旧資格情報の無効化を設計する。2025年秋午後問3では、本文に示された認証基盤で実現できる代替策を選ぶ。

### 11.2 シーケンス図の読み方を一段具体化する

| 受信する値 | 受信者 | 本文で探す照合 |
|---|---|---|
| 認可コード | クライアント、認可サーバ | 自分が開始した要求か、正しい交換先か、PKCEの照合はあるか |
| IDトークン | RP | 署名鍵・発行者・宛先・期限、要求に対応するnonce |
| アクセストークン | API | そのAPI向けか、許可スコープと対象データの認可は十分か |
| SSHホスト鍵 | SSHクライアント | 信頼できる経路で得たフィンガープリントと一致するか |
| クライアント証明書 | 接続先 | 信頼連鎖・失効・用途、その証明書に対応する秘密鍵を持つか |

2021年秋午後Ⅰ問1では、SSHのホスト鍵確認と利用者の公開鍵認証を分ける。パスフレーズは利用者側で秘密鍵を復号するためのもので、SSHサーバへ送って認証するものではない。

`state`・`nonce`・PKCEは、初学時は3.4の役割で整理する。実装時には組合せによる保護もある。[OAuthセキュリティBCP（RFC 9700）](https://www.rfc-editor.org/rfc/rfc9700.html)では、認可サーバの対応を確認した適切なPKCEをCSRF防御に使える条件も示されている。「PKCEはCSRFと一切関係がない」と丸暗記しない。
