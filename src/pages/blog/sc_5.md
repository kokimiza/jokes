インシデント対応の問題では、本文にログの抜粋が並び、「何が起きたか」「次に何を調べるか」「何を止めるか」を答えさせる。ログの書式や用語は問題文に説明が付くので、イベントIDを丸暗記する必要はない。必要なのは、記録から言えることと言えないことを分けて書く力である。

この章は、攻撃経路、ログの観測範囲、時系列、封じ込め、復旧への引渡しの順で読む。ログから感染端末を列挙するだけでなく、認証情報・セッション・共有ファイル・バックアップへ影響が広がっていないかを追う。技術調査と並行して、誰が遮断や公表を決めるかも整理する。

## 1. 出題実績と予想

| 回 | 題材 | 講評で指摘された点 |
|---|---|---|
| 2023秋 問1 | XSSによる侵害への対応 | HTMLやスクリプトを確認すれば分かる攻撃の手順を読み落とした |
| 2023秋 問3 | CIサービスの侵害 | コンテナがどの権限で動くかの理解が浅い |
| 2024秋 問1 | 社内システムのログ調査、マルウェアによる持出し | どのログを確認するかを書いていない。特別な権限なしで持ち出しているのに「アクセス権を最小にする」と答えた |
| 2024秋 問3 | カード情報の漏えい調査 | アクセスログに何が残るかを読まずに「盗聴」と答えた |

次回の予想は次のとおり。

- **◎ ランサムウェア**：旧形式では2022秋の午後Ⅱ問2（EDR）まで毎年のように出ていたが、新形式でEDRのログを使う本格的な問題はまだない。2025年も国内で、業務が長く止まる被害が続いた。VPN機器からの侵入、ADの乗っ取り、バックアップの削除、復旧の判断までを一続きで問う形が考えられる。
- **○ クラウドの侵害調査**：監査ログ（API呼出しの記録）から、漏れたキーが何に使われたかを追う問題。2023秋問3の延長にある。
- **○ 内部不正**：2023秋問4と2024秋問1の流れ。正規の権限で持ち出す行為は、権限の見直しでは防げない。

## 2. 人手によるランサムウェア攻撃の流れ

最近のランサムウェアの多くは、侵入した攻撃者が組織の中を調べ、権限を広げてから一斉に暗号化する。次の表は典型的な順序で、必ずこの順に進むわけではない。

| 段階 | よくある手口 | 残りやすい痕跡 |
|---|---|---|
| 侵入 | VPN装置や公開サーバの脆弱性、漏れた認証情報、メール | VPNログの普段と違う接続元・時間帯 |
| 実行・常駐 | PowerShell、サービスやタスクの登録、アカウントの作成 | プロセスの生成記録、サービスの登録記録 |
| 資格情報の窃取 | LSASSのメモリの読取り | EDRのアラート、LSASSへのアクセス記録 |
| 横展開 | RDP、SMB、リモート実行ツール | 別の端末からのネットワークログオン |
| 外部との通信 | HTTPSで一定間隔に通信する | プロキシ・DNSログに、同じ宛先への周期的な通信 |
| 持出し | 圧縮してクラウドストレージへ送る | 圧縮ファイルの作成、送信量の多い通信 |
| 暗号化 | バックアップの削除、一斉の暗号化 | シャドウコピーの削除、大量のファイル書換え |

暗号化に加えて「盗んだ情報を公開する」と脅す手口（二重恐喝）では、バックアップから戻せても情報漏えいとしての対応が要る。個人データが含まれていれば、個人情報保護委員会への報告と本人への通知も検討する（[第7章](/blog/sc_7)）。

### 2.1 初期侵入と暗号化の時刻は違う

月曜の朝に暗号化を検知しても、侵入がその直前とは限らない。数週間前にVPNから入り、特権を取り、バックアップを調べてから暗号化する場合がある。暗号化時刻だけを調査開始点にすると、侵入口と持出しを見落とす。最初の不審なログオン、資格情報の変更、常駐の登録まで遡り、その時点より前のバックアップも確保する。

侵入時に使った資格情報と、横展開に使った資格情報も分ける。一般利用者でVPNに入り、管理者の認証情報を別端末で盗んだ場合、最初のIDだけを止めても攻撃は続く。端末、アカウント、使用された鍵やトークンを別々の一覧にし、それぞれの利用先を調べる。

### 2.2 正規ツールの実行だけで攻撃と決めない

PowerShell、リモート管理、圧縮、クラウド転送は正規業務でも使う。実行ファイル名だけで判定せず、親プロセス、引数、実行ユーザー、保存場所、接続先、普段の利用と変更申請を合わせて見る。署名済みの正規ツールでも悪用されるので、「電子署名があるから安全」という除外もできない。

IOCはファイルハッシュや通信先など個別の痕跡、TTPは資格情報窃取やサービス経由の実行などの行動である。IOCで同じものを横断検索し、TTPでファイル名・通信先を変えた攻撃も探す。ハッシュ不一致は別ファイルを示すだけで、無害を示すわけではない。

## 3. Windowsのログの読み方

試験ではイベントIDの意味が問題文に書かれることが多い。それでも次のものは見てすぐ分かると、読む時間を短くできる。

| ID | 内容 | 読み方 |
|---|---|---|
| 4624 / 4625 | ログオンの成功 / 失敗 | 種別と送信元アドレスで、どこから入ったかを追う |
| 4672 | 特権を割り当てたログオン | 管理者権限のアカウントが使われた |
| 4688 | プロセスの生成 | コマンドラインを記録していれば実行内容が分かる |
| 7045 | サービスのインストール | リモート実行ツールや常駐に使われる |
| 1102 | セキュリティ監査ログの消去 | 正規の消去作業か、痕跡隠蔽かを他の記録と確認する |

4624のログオン種別は、3がネットワーク（ファイル共有やリモート実行）、10がRDPである。

```
10:02  FS01  4624  種別3   user=adm-ops  src=10.1.20.15
10:03  FS01  7045  サービス名=ランダムな文字列  パス=C:\Windows\Temp\x.exe
10:05  FS01  4688  親=services.exe  子=x.exe
```

この3行から言えるのは、10.1.20.15からadm-opsでネットワークログオンがあり、その直後にTempフォルダーのプログラムがサービスとして登録・実行されたことまでだ。横展開を疑う根拠にはなるが、送信元の端末が乗っ取られたのか、どうやって資格情報を取ったのかまでは、この3行では決まらない。正規の管理作業の記録と照らし、送信元の端末のEDRの記録を調べる。

イベントIDと攻撃名を一対一に結び付けない。4672は特権を持つアカウントのログオンを示すだけで、脆弱性を使った権限昇格を意味しない。種別3もSMBに限らない。

### 3.1 同じログオンをどう結び付けるか

接続先で記録されたログオンIDを、その端末内のプロセスや権限イベントと対応付ける。ログオンIDは全端末共通の利用者識別子ではない。同じユーザー名が複数ドメインにある場合は、ドメイン名やSIDも使う。プロセスIDも再利用されるので、PIDだけでなく起動時刻や、取得できる場合は一意なプロセス識別子を組み合わせる。

7045はサービス制御マネージャーのSystemログに現れる一方、4624等はSecurityログである。収集対象がSecurityだけならサービス作成を見落とす。4688のコマンドラインやPowerShellの詳細ログも、監査設定を有効にしていなければ後から取り戻せない。試験では本文の取得項目を優先し、記録されない項目を前提にしない。

プロセスの親子関係も手掛かりになる。WordやExcelの子としてPowerShellが起動していれば、マクロによる実行を疑う。

### 3.2 EDRの検知と処置を区別する

EDRが「検知」したことと、実行を「阻止」したことは違う。検知時刻、実行時刻、隔離時刻、遮断の成否を並べる。実行後に隔離した場合は、その間にファイル読出しや通信が終わった可能性がある。自動隔離が成功した端末でも、共有サーバ側の処理や発行済みクラウドトークンまで止まるとは限らない。

EDRが一部端末に未導入、長期オフライン、センサー停止なら、集中画面で何も見えないことを正常と扱わない。最終通信時刻と稼働状態を調べ、必要なら端末そのものや他のログを確認する。除外設定が広すぎる場合は、その範囲を使った攻撃も考える。

## 4. ADを狙う攻撃

ADを乗っ取られると、組織中の端末に影響が及ぶ。

| 攻撃 | 概要 | 対策 |
|---|---|---|
| 資格情報の窃取 | LSASSのメモリから認証情報を読む | Credential Guard、特権アカウントで一般の端末にログオンしない |
| Pass-the-Hash | 盗んだNTLMハッシュで別の端末に認証する | LAPS、NTLMの制限 |
| Kerberoasting | サービスアカウントのチケットを取り、手元でパスワードを解析する | サービスアカウントに長いパスワード、gMSA |
| Golden Ticket | KRBTGTの鍵でTGTを偽造する | 侵害除去とDC間の複製・チケット寿命を考慮して、管理された手順でKRBTGTを2回リセットする |

ドメイン管理者がふつうの端末にログオンすると、その端末のメモリに資格情報が残り、盗まれる。管理者は、ドメインコントローラーと管理専用の端末にだけログオンする。

### 4.1 パスワードを変えたのに止まらない理由

Pass-the-HashではNTハッシュそのものが認証に使われる。平文パスワードを解読できたという意味ではない。Kerberoastingでは取得したサービス用チケットをオフラインで解析し、弱いサービスアカウントのパスワードを推測する。オンラインのアカウントロックはこの解析を止めない。長くランダムな秘密やgMSAで耐性を上げ、サービスアカウントの過剰な権限を削る。

Golden Ticketでは利用者パスワードでなくKRBTGTの鍵が問題になる。現在と直前の鍵を扱う仕組みのため、二回のリセットが必要になるが、連続して機械的に行うと認証障害を起こしうる。復旧した安全な管理環境から、複製とチケットの状態を考慮して行う。攻撃者がDCを支配したままでは新しい鍵も盗まれるため、鍵変更だけでは根絶にならない。

NTLMリレーは、認証のやり取りを別のサービスへ中継して認証させるもので、盗んだハッシュを使う攻撃とは異なる。SMB署名や適切なチャネル保護等、対象プロトコルに応じた対策を選ぶ。「MFAを入れる」をすべての内部認証への万能策にしない。

## 5. 通信のログ

外部の指令サーバとの通信（C2）は、同じ宛先へのHTTPSが一定の間隔で続く、業務時間外にも続く、登録されたばかりのドメインやIPアドレスへ直接つなぐ、といった特徴を持つ。

持出しの調査では、プロキシログで端末ごとの送信量が普段より極端に多い通信を探し、圧縮ファイルを作った時刻と並べる。業務で使っていないクラウドストレージへの通信も手掛かりになる。

端末がDNSを社内のキャッシュDNS経由でしか使えないようにしておけば、DNSのログで不審なドメインを見つけられる。長くて意味のないサブドメインへの問合せが大量にあれば、DNSを使ってデータを運ぶ手口（DNSトンネリング）を疑う。

### 5.1 通信成功と情報漏えいの確定は違う

FWの許可ログは通信がポリシーで許された記録であり、必ずアプリの処理が成功したことを示さない。DNS問合せは名前を引いた記録であり、接続やファイル送信の成功までは示さない。HTTP 200もサーバが応答したことの材料で、送信したデータの内容が分かるとは限らない。

大量送信の前に機密ファイルの読出しと圧縮があり、同じプロセスが外部へ送っているなら、持出しを強く疑える。ただし暗号化された通信量だけから、どの個人のどの項目が漏れたかまでは確定できない。ファイル監査、アプリのエクスポート記録、クラウドのオブジェクト取得ログなど、内容と操作対象を特定できる記録を追加する。

### 5.2 クラウドとSaaSの調査

クラウドでは監査ログの主体、ロール・セッション、送信元、API名、対象リソース、成功・失敗を読む。一時的な認証情報が外部IPから使われていても、元のVMが外部へ移ったという意味ではなく、資格情報が持ち出された可能性がある。STS等の発行履歴と、元のワークロードのログを結び付ける。

ストレージのデータ取得ログやSaaSの閲覧・ダウンロード監査は、管理操作のログと別設定・別契約の場合がある。管理ログに削除がないことだけで、データ持出しもないとは言えない。調査時は取得可能な期間を確認し、期限切れになる記録の保全を早める。

IdPの不審ログインだけで終わらず、その後のMFA登録、アプリ同意、転送ルール作成、共有リンク発行まで追う。メールアカウントを戻しても、外部転送やOAuthの権限付与が残れば持出しが続くことがある。

## 6. 時系列の組み立て方

1. **時刻をそろえる。** 機器ごとのタイムゾーン（UTCと日本時間の9時間差）と時計のずれを補正する。
2. **アドレスを端末と人に対応付ける。** DHCPの払出し、VPNの割当て、NATの変換の記録を使う。
3. **確かな痕跡から始める。** EDRのアラートや、確認できた不審な通信先を起点にする。
4. **前後に広げる。** その端末にどこからログオンしたか（前）、その端末からどこへつないだか（後）をたどる。
5. **他にないか探す。** 同じファイルのハッシュ値、通信先、アカウントを、他の端末の記録から検索する。

記録がないときは、理由の候補を挙げる。実行されていない、監査の設定が無効、保存期間を過ぎた、監視している位置を通っていない、消された、別の経路を使った、のいずれかだ。2019秋の午後Ⅰ問3では、C2につながっていない端末を「感染していない」と決めつけないことが問われた。

Webのアクセスログは、設定によってURLとクエリ文字列を残すが、POSTの本文は残さない。2024秋問3では、カード情報がクエリパラメータで送られていたため、アクセスログから被害を受けた利用者を特定できた。逆に言えば、ログに機密情報が残ること自体が漏えいの経路にもなる。

### 6.1 ログを結合する具体例

次は学習用の架空の記録で、時計は同期しているとする。

| 記録 | 時刻 | 値 |
|---|---|---|
| 外部サービス | 01:15 UTC | `198.51.100.20:62000` から不正送信 |
| NAPT | 10:15 JST | 上記を `10.1.2.30:51000` へ対応付け |
| DHCP | 09:00〜12:00 JST | `10.1.2.30` は端末PC30へ貸出し |
| EDR | 10:14 JST | PC30のプロセスPが圧縮ファイルを作成 |

まずUTCに9時間を加えて時刻をそろえ、外部のIP・ポートからNAPT、内部IPと時刻からDHCPをたどる。PC30という端末が分かった後に、そのプロセスと利用者を調べる。この時点で社員本人が不正をしたとは断定できない。マルウェアや盗まれたセッションによる操作もありうる。

時計に数分のずれがあるなら、ログの原本時刻を残したまま補正値を別列に記録する。上書きで時刻を書き換えると、後で補正の根拠を再確認できない。秒単位の前後関係が重要な場合は、ずれの範囲内で順序を断定しない。

## 7. 「調べる」を答案にする

2024秋問1の講評は、「どのログを確認するか」が書かれていない答案が多かったと指摘している。調査の答案には、対象、使う記録、条件、確かめたいことを入れる。

| 弱い答案 | 点になる答案 |
|---|---|
| ログを調べる | FS01のログオン記録で、10時台のadm-itの接続元を確認する |
| 情報漏えいを確認する | プロキシログで、PC-Kから外部への送信量と時刻を確認する |
| 他の端末も調べる | EDRの記録で、同じハッシュ値のファイルを実行した端末を検索する |

事実と推測も分けて書く。

| | 例 |
|---|---|
| 事実 | 02:20にPC-Kで不明なプロセスがLSASSにアクセスし、02:55にadm-itでFS01へログオンした |
| 推測 | PC-Kでadm-itの資格情報が盗まれ、FS01への横展開に使われた可能性がある |
| 追加で調べること | PC-KでのEDRの記録、adm-itがPC-Kを使った履歴、FS01で実行された処理 |

### 7.1 仮説を反証できる確認を選ぶ

「PC-Kで資格情報を盗まれた」という仮説なら、LSASSにアクセスしたプロセス、管理者がPC-Kへログオンした履歴、その後の管理者の利用先を調べる。「ファイルを外へ送った」なら、読出しと圧縮に加えて、プロキシ等で外部転送の成否を調べる。単に不審な記録を増やすのでなく、どの仮説を確かめる確認かを対応付ける。

「ほかの端末への感染がないことを確認せよ」という設問でも、記録だけで完全な不存在を証明できるとは限らない。本文の収集範囲と保存期間を使い、同じ痕跡を検索する対象・期間・条件を具体化する。記録の欠落があるなら、端末調査等で補う必要がある。

## 8. 封じ込めと証拠の保全

### 8.1 何をどう止めるか

| 手段 | 効果 | 注意 |
|---|---|---|
| EDRによる端末の隔離 | 管理用の通信以外を遮断する。電源は入ったままなのでメモリの証拠が残る | 業務への影響 |
| アカウントの無効化 | そのアカウントによる新たな認証等を止める | 発行済みセッション・トークン・チケットは別に扱う |
| 通信先の遮断 | FW・プロキシ・DNSで止める | 別の通信先に切り替えられることがある |
| VPNや外部接続の停止 | 侵入口を塞ぐ | 事業への影響が大きく、経営の判断が要る |

電源を切ると、メモリ上の情報（動いているプロセス、通信、メモリだけで動くマルウェア、暗号鍵）が消える。まずネットワークから切り離す。ただし2018秋の午後Ⅱ問2の講評のとおり、即座に切り離すことには長所と短所がある。被害が広がり続けているなら封じ込めを急ぎ、取れる範囲で証拠も取る。OTや認証基盤を止めると安全や業務に響くので、代わりの手段も含めて判断する。

隔離する範囲は、侵害が確認された端末だけではない。盗まれたと見られるアカウントがログオンした端末も対象にする。攻撃者がそのアカウントで既に横展開しているかもしれないからだ。

### 8.1a 端末・ID・通信を組み合わせて止める

PCだけ隔離しても、盗まれたキーは別の場所で使える。IDだけ止めても、別IDや既存セッション、既に常駐したサービスは残りうる。封じ込めでは、端末隔離、資格情報の無効化と再発行、セッションの失効、侵入口の修正、C2の遮断を、確認した経路に合わせて組み合わせる。

ただしDCやOTのような重要機器は、一律隔離すると全社認証や安全な制御を止めることがある。確認された被害、到達範囲、代替経路、停止した場合の影響を示し、権限者が判断できる形にする。暗号化が進行しネットワーク隔離だけでは止まらない場合は、証拠より被害抑止を優先して停止が必要になることもある。「必ず電源を切らない」を無条件の規則にしない。

### 8.2 証拠の保全

- 消えやすいもの（メモリ、通信の状態）と、すぐ上書きされるログから先に取る。
- ディスクは複製を取り、ハッシュ値を記録する。分析は複製に対して行う。
- 誰が、いつ、何を取得し、誰に渡したかを記録する。
- ログを別のサーバに転送しておけば、攻撃者に消されても残る。保存期間が短いと、侵入した時期までさかのぼれない。

ハッシュ値は取得後のデータが変化していないかを比較する材料で、取得前から正しいデータだったことや取得者の身元まで保証しない。取得方法、日時、担当者、媒体、保管場所、受渡しを記録し、アクセスできる人を制限する。稼働中の機器の採取では状態が変わることもあるので、実施した操作も残す。

メモリやパケットにパスワード・個人情報が含まれる場合がある。分析用の環境と原本を分け、共有範囲を絞る。未知のファイルを一般業務端末で実行しない。解析用環境は業務・管理ネットワークから分離し、外部通信も制御する。

### 8.3 体制

SOCがログを監視して一次分析をし、CSIRTが対応の全体をまとめて社内外と調整する。事業を止めるか、公表するかといった判断は経営層が行う。外部の連絡先には、フォレンジック事業者、JPCERT/CC、警察、個人情報保護委員会、取引先がある。

役割名よりも、検知後に誰が何分・何時間以内に連絡し、誰が隔離を実行・承認するかを決める。担当者不在や社内メール侵害に備え、代替連絡手段も用意する。経営への初報は、確定事実、未確認事項、影響する業務、実施した対処、次の判断と期限を分ける。原因が確定するまで報告を待っては、拡大防止や法定報告が遅れる。

身代金は払わないのが原則である。払っても復号やデータの削除は保証されず、攻撃者の資金になる。

## 9. 再発防止策は攻撃の段階に合わせる

| 段階 | 対策 |
|---|---|
| 侵入 | VPN装置の修正の適用、MFA、公開している資産の棚卸し |
| 実行 | アプリケーションの実行制御、PowerShellの利用制限とログの取得 |
| 資格情報の窃取 | Credential Guard、特権アカウントの使い分け、LAPS |
| 横展開 | 端末間のSMB・RDPを止める、セグメントの分離 |
| 検知 | 全端末へのEDRの導入、ログの集約と保存期間の延長 |
| 暗号化 | オフラインや削除できないバックアップ、復旧の訓練（[第6章](/blog/sc_6)） |

設問が「持出しを防ぐ対策」なら、持出しの段階に効く対策を書く。2024秋問1では、マルウェアが特別な権限なしにファイルを持ち出していたため、アクセス権を絞っても防げなかった。

### 9.1 根絶と復旧の完了条件

封じ込めは被害の拡大を止めること、根絶は侵入口・常駐・不正アカウント等を除くこと、復旧は業務を安全に再開することである。マルウェアのファイルを一つ消しただけで、他の常駐や盗まれた資格情報まで消えたとは言えない。侵害機器は信頼できるイメージから再構築し、安全な端末から認証情報を更新することを検討する。

復旧先は隔離環境で構築し、バックアップの健全性、修正、設定、業務データの整合性を検証して段階的に再接続する。監視期間と再隔離の条件を定める。詳細なバックアップ・依存関係は[第6章](/blog/sc_6)で扱う。

対応後は、最初の侵入から検知まで、検知から隔離まで、業務再開までの時間を測る。通知を出しても担当者が見ていなかったなら、追加すべき対策は検知ルールだけではなく、当番・連絡・実行権限の見直しである。[NIST SP 800-61 Rev.3](https://csrc.nist.gov/pubs/sp/800/61/r3/final)も、対応を平常時のリスク管理と継続的な改善に組み込んでいる。
