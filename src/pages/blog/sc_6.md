管理系の問題といっても、規格の名前を答えさせることはほとんどない。問われるのは、脆弱性の情報を自社の資産に当てはめて優先度を決める、リスクを具体的な場面として書く、侵害された後に早く戻すための準備を挙げる、といった実務の判断だ。

## 1. 出題実績と予想

| 回 | 題材 | 講評で指摘された点 |
|---|---|---|
| 2023秋 問3 | CIサービスの侵害 | コンテナの権限と動作の理解 |
| 2023秋 問4 | 委託先を含む個人情報のリスクアセスメント | リスクが具体的でなく、被害の大きさや頻度を評価できない |
| 2025春 問1 | サプライチェーン、委託先の管理、開発プロセス | SBOMの利点を問われて定義を書いた。SAST・DAST・IASTの違い |
| 2025春 問2 | 脆弱性の深刻度と対応優先度 | CVSSv3のAC（攻撃条件の複雑さ）をC（機密性への影響）と取り違えた。CVSSの現状値とEPSSの使い方 |
| 2025春 問4 | 公開資産の管理（ASM）とKEV | KEVを現状の評価に使うことを理解していない |

次回の予想は次のとおり。

- **◎ ランサムウェアからの復旧と事業継続**：2025秋問4の講評は「被害に至る経緯の解明より事業の復旧を優先する場合もある」と書いている。バックアップの守り方、復旧の順序、RTOを満たせるかの検証が狙われる。
- **○ 委託先とクラウド事業者の管理**：2025春問1の続き。国内では取引先にも一定の対策水準を求める動きが続いている。契約で何を決めておくか、委託先で事故が起きたときに何を求めるか。
- **○ 脆弱性管理**：2025春に2問出た。SBOMの使い方、CVSS・EPSS・KEVの使い分けは、別の問題の設問としても出しやすい。

## 2. 脆弱性管理

### 2.1 流れ

1. 資産を把握する。製品、バージョン、公開しているか、管理者は誰かを台帳にする。
2. 情報を集める。ベンダーの公表、JVN、CISAのKEVカタログ。
3. 自社が該当するかを判断する。脆弱な機能を使っているか、外から届くか、認証が要るか。
4. 優先度を決める。
5. 修正を当てる。すぐに当てられないなら、機能の無効化や接続元の制限で回避し、監視を強める。
6. 当たったかを確認し、再スキャンする。

### 2.2 SBOM

SBOMは、ソフトウェアに含まれる部品（ライブラリとそのバージョン）の一覧である。2025春問1の講評は、利点を問われて「部品表である」と定義だけを書いた答案が多かったと指摘している。利点は「新しい脆弱性が公表されたとき、その部品とバージョンを含む自社の製品や稼働中のシステムをすぐに特定できる」ことだ。

SBOMがある、イメージに署名がある、というだけでは、中身が安全だとは言えない。

### 2.3 CVSS、EPSS、KEV

| 指標 | 中身 | 使い方 |
|---|---|---|
| CVSS | 技術的な深刻度。v3には基本値・現状値・環境値がある | 設問が指定した版の指標で読む |
| EPSS | 今後30日以内に悪用される確率の推定 | 深刻度が高くても悪用されにくいものと区別する |
| KEV | 実際に悪用が確認された脆弱性の一覧 | 該当すれば最優先で対応する |

CVSSv3のACは攻撃条件の複雑さ、Cは機密性への影響である。2025春問2ではここを取り違えた答案が多かった。

同じ問題で正答率が低かったのが、CVSSの現状値とEPSSの手間の違いだ。CVSSの現状値は、攻撃コードが出回っているか、修正が出ているかといった情報を自分で集めて評価し直す必要がある。EPSSは公表されている値を取ってくるだけで済む。

優先度は、インターネットに公開している、実際に悪用されている、重要な業務に関わる、の三つが重なるものを最優先にする。VPN装置やFWなど境界の機器はその典型である。

## 3. 開発基盤とサプライチェーン

### 3.1 CI/CD

CIサービスには、本番環境へのデプロイ権限、クラウドの認証情報、署名鍵が集まる。侵害されたとき、どの秘密情報を読まれ、どこまで使われるかを考える。

| リスク | 対策 |
|---|---|
| 秘密情報の漏えい | 長期間有効なキーを置かない。OIDC連携で、ジョブの実行時だけ有効な認証情報を発行する |
| 過剰な権限 | パイプラインごとに必要な権限だけを与える |
| 外部からの持込み | フォークからのプルリクエストでは秘密情報を使わせない |
| 外部のアクションやプラグイン | タグではなくコミットのハッシュで固定する |
| 成果物の改ざん | 成果物に署名し、デプロイ前に検証する |
| 承認なしのデプロイ | 本番へのデプロイに承認を必須にする |

漏えいが分かったら、登録していた秘密情報をすべて失効させて作り直す。そのうえで、漏れていた期間にそれらが使われていないかを、クラウドやリポジトリの監査ログで確かめる。

コンテナはホストとカーネルを共有する。特権モードで動かしたり、ホストのソケットやディレクトリを共有したりすると、コンテナの中から外へ出られる。2023秋問3の講評は、コンテナがどの権限で動くかの理解を求めている。

### 3.2 部品の取り込み

社内用のパッケージ名と同じ名前を公開リポジトリに登録され、そちらを取り込んでしまう攻撃（依存関係の混乱）や、似た名前のパッケージ（タイポスクワッティング）に注意する。社内用の名前空間を予約し、取得元を社内リポジトリに固定する。

### 3.3 開発プロセスに組み込む検査

| 手段 | 対象 | 足りないところ |
|---|---|---|
| SAST | ソースコードを実行せずに解析 | 実行時の条件や業務上の権限は扱いにくい |
| DAST | 動いているアプリに外からリクエストを送る | ログインや画面遷移の設定が要る |
| IAST | テスト実行中のアプリの内部を観測 | テストで通らなかった経路は見ない |
| SCA | 依存部品と既知の脆弱性を照合 | 自社コードの認可不備は見つからない |

開発プロセスを問われたら、検出（レビュー、診断）、修正、再テストという工程で答える。2025秋問1では、WAFの導入やログ分析といった運用の対策を書いた答案が多かった。

## 4. 委託先の管理

| 段階 | 決めておくこと |
|---|---|
| 選定 | セキュリティの体制、認証の取得状況、過去の事故 |
| 契約 | 求める対策、事故が起きたときの報告期限と連絡先、監査の権利、再委託の条件、終了時のデータの返却と削除 |
| 運用 | 定期的な評価、アクセス権の見直し、リモート接続の管理 |
| 終了 | アカウントと接続経路の削除、データ削除の確認 |

再委託は事前承認制にし、再委託先にも同じ水準を求める。保守のためのリモート接続は、必要なときだけ有効にし、接続元を限り、MFAを使い、担当者ごとにアカウントを分けて操作を記録する。

外部に委託しても、説明の責任は委託元に残る。個人データを委託した場合、委託元には委託先を監督する義務がある。

## 5. リスクアセスメント

リスクの特定（資産・脅威・脆弱性・既存の対策を洗い出す）、分析（影響と起こりやすさを見積もる）、評価（受容できる水準と比べて優先度を決める）を経て、対応を選ぶ。

| 対応 | 中身 | 例 |
|---|---|---|
| 低減 | 対策で起こりやすさや影響を下げる | MFA、バックアップ |
| 回避 | 原因となる活動をやめる | カード情報を自社で持たない |
| 移転 | 他者と分担する | サイバー保険、外部委託 |
| 受容 | 対策をとらずに受け入れる | 経営層が承認し、残るリスクとして記録する |

2023秋問4の講評は、特定したリスクが具体的でなく、被害の大きさや頻度を評価できない答案が多かったと指摘している。リスクは「誰が、どこから、何をして、何が困るか」で書く。

- 弱い：個人情報が漏えいするリスク
- 具体的：配送担当者が、配達に要らない顧客一覧を共有フォルダーから私物の記録媒体にコピーして持ち出す

本文が内部の人間を脅威として指定しているなら、外部からの攻撃の話に置き換えない。正規の閲覧権限で実行できる持出しには、ログインを強くしても効かない。

攻撃シナリオでリスクを分析する方法もある。「保守事業者の接続用の認証情報が漏れる → 保守用VPNから工場のネットワークに入る → 制御サーバを暗号化する → 生産が止まる」のように経路を書き、各段階に防ぐ・気づく・対応する手段があるかを確かめる。

## 6. 事業継続と復旧

### 6.1 BIAとRTO・RPO

業務ごとに、止まったときの影響（売上、法令、顧客、安全）と、止まってよい時間を分析し、先に戻す業務を決める。これがBIA（業務影響度分析）である。

| 指標 | 意味 | 決め方 |
|---|---|---|
| RTO | どれだけの時間で戻すか | 業務が止まっていられる時間 |
| RPO | どの時点のデータまで戻すか | 失ってよいデータの量 |

RPOが1時間なら、少なくとも1時間ごとにバックアップか複製が要る。ただしバックアップの間隔を短くしても、転送、復元、動作確認に時間がかかればRTOは満たせない。RTOとRPOは別々に確かめる。

### 6.2 ランサムウェアに耐えるバックアップ

| 要件 | 中身 |
|---|---|
| オフライン・変更不可 | ネットワークから切り離す、または一定期間は変更も削除もできない設定にする |
| 管理者の分離 | バックアップの管理アカウントをADと分ける。ADを乗っ取られても消されない |
| 世代 | 侵入から暗号化までの潜伏期間を考え、十分に古い世代まで残す |
| 復元テスト | 実際に戻せるか、戻すのにRTO以内で済むかを測る |
| 複数の保管先 | 3つのコピー、2種類の媒体、1つは遠隔地（3-2-1） |

本番とDRサイトをリアルタイムで同期していると、暗号化されたデータも同期される。同期とは別に、過去の時点へ戻せるバックアップが要る。

### 6.3 復旧の順序

1. 侵入口を塞ぐ。脆弱性を直し、乗っ取られたアカウントを止める。塞がずに戻すと、また入られる。
2. 認証基盤（AD）を戻して安全な状態にする。他のシステムが依存しているため。
3. BIAで優先度が高い業務のシステムを戻す。
4. 残りのシステムを戻す。

戻すバックアップには、侵入より前の世代を選ぶ。マルウェアや攻撃者が作ったアカウントが含まれていないかを確かめてからつなぐ。

### 6.4 OT（工場の制御系）

工場のSCADAや制御機器は、止まること自体が損害になり、安全にも関わる。事務用のPCと同じLANにある、保守事業者がリモートで接続する、USBメモリでデータを受け渡す、といった接点が侵入経路になる。通信の帯域を埋められるだけでも制御の通信が止まる。

2025秋問4の講評は二つのことを指摘している。マルウェアは脆弱性を突いたり正規の利用者をだましたりして動くので、利用者認証を強くしても効果が薄いこと。復旧の準備を問われたら、攻撃を止める手段ではなく、平常時に用意しておくもの（バックアップ、予備の機器、手順、訓練）を書くこと。

## 7. 管理の枠組み

| 枠組み | 中身 |
|---|---|
| ISO/IEC 27001 | ISMSの要求事項。リスクアセスメントに基づいて管理策を選ぶ |
| NIST CSF 2.0 | 統治・識別・防御・検知・対応・復旧の6機能。2.0で統治（Govern）が加わった |
| サイバーセキュリティ経営ガイドライン | 経営者が認識すべき原則と、担当者に指示すべき重要項目 |
| ISMAP | 政府がクラウドサービスを調達するときの評価制度 |

開発者が本番環境へ直接リリースできる、承認する人と実行する人が同じ、といった状態は不正や誤りを見逃す。CI/CDでデプロイに承認を必須にするのも、職務の分離の一つである。

経営層に判断を求める設問では、判断に必要な材料を挙げる。システムを止めるなら、被害が広がる見込み、止めたときの業務への影響、代わりの手段。リスクを受け入れるなら、残るリスクの中身、起きたときの影響、受け入れる期間と見直す時期。
